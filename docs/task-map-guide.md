# 用户任务地图怎样使用

## 它回答什么

地图不以菜单或按钮为主线，而是回答：谁在什么情况下，要完成什么工作，交出什么结果，遇到异常后如何继续。

当前导出包含 4 类角色、6 个阶段、31 项任务和 13 个场景。范围覆盖与实现状态分别记录，不因列在地图中就视为已开发。

## 字段与需求追踪

| 字段 | 含义 |
| --- | --- |
| role / stage / title | 谁，在业务的哪一段，要完成什么 |
| trigger / inputs | 什么时候发生，需要什么输入 |
| steps / output / done | 怎样做，产出什么，怎样才算完成 |
| exception | 不满足前提或操作失败后怎样继续 |
| availability / current_support / gap | 当前支持、外部依赖与剩余缺口 |
| acceptance / verification | 可执行的检查条件与证据边界 |
| source / frequency / research_state | 依据来自哪里，哪些只是业务假设 |
| story_ids / scenario_ids / evidence_ids | 与用户故事、跨任务情境和证据连接 |

`planning` 层还包含活动、故事、流程、版本、研究队列与度量建议。部分证据 ID 引用本地历史报告，本仓库没有公开所有原始报告；可以从本仓库验收摘要理解当前公开范围，不能假设每个 ID 都有可下载的公开附件。

## 一个例子

T08「接手同事交来的事项」的目标是接住同一事项和历史，不是简单点击“分派”。验收应检查接班者能看到现有材料与下一步，不能跨空间误分派；材料变化后要按当前版本接受。

因此地图要连接交接接受、材料版本与待办，而不是只标注“有工单页面”。

## 维护顺序

1. 从完整案例或真实业务观察记录未满足的结果。
2. 修订触发、异常与完成条件，再判断产品能覆盖到哪一步。
3. 将缺口拆成可交付故事和预先冻结的验收条件。
4. 修改产品，通过实际界面走查；接口与单元检查提供补充证据。
5. 回写状态与局限，保留失败记录，安排下一次真实业务验证。

当前任务频率与优先级尚无真实客服使用样本，不能把推演写成访谈事实。
